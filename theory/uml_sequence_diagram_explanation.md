# UML Sequence Diagram для проекта Шнопс 66

## Используемая схема

**UML Sequence Diagram (Диаграмма последовательности взаимодействия)**

Из лекции "Базы данных для игровых приложений" - страницы 13-16.

## Конкретный вариант

**Игра всегда для двух игроков с системой приглашений** (стр. 14-16)

### Почему именно этот вариант?

1. **Шнопс 66 - игра строго на 2 игроков**
   - Не подходит вариант с игровыми комнатами (стр. 17-20)
   
2. **Система приглашений между пользователями**
   - Пользователь видит список других пользователей
   - Может отправить приглашение конкретному игроку
   
3. **Приглашение имеет срок действия (таймер)**
   - Если не принято за время - становится недоступным
   - Предотвращает ситуацию "отправитель ушёл, а игра началась"

## Архитектура клиент-сервер

**Вариант 3 из лекции (стр. 12):**

```
HTTP-клиент → HTTP-сервер → SQL-сервер
              API
```

- API представляет собой набор HTTP-запросов
- Клиенты НЕ могут подключаться к SQL-серверу напрямую
- HTTP-сервер реализует логику игры и контролирует доступ

## Тип взаимодействия

**Polling (Short Polling)** - стр. 5

- Клиент периодически (каждые 3-5 сек) отправляет запросы серверу
- Сервер сразу отвечает на запросы
- Сервер НЕ может сам инициировать отправку данных клиенту

### Почему Polling?

- Простота реализации
- Поддерживается всеми серверами
- Для карточной игры не критична задержка в несколько секунд

### Альтернативы (не используются в проекте):

- Long Polling - сервер ждёт события перед ответом
- WebSocket - двустороннее соединение
- SSE (Server-Sent Events) - односторонняя отправка с сервера

## Ключевые принципы UML Sequence Diagram

### Основные участники (акторы):

1. **Пользователь A** (user)
2. **Клиентское приложение A** (client)
3. **HTTP-сервер** (server)
4. **SQL-сервер / СУБД** (database)
5. **Клиентское приложение B** (client)
6. **Пользователь B** (user)

### Последовательность взаимодействия:

#### 1. Авторизация

```
User A → Client A: вводит логин/пароль
Client A → Server: login(login, password)
Server → Database: проверка существования логина и правильности пароля
Database → Server: результат проверки
Server → Client A: успех/ошибка
Client A → User A: показывает результат
```

#### 2. Получение списка пользователей

```
Client A → Server: get_users_list(login, password)
Server → Database: проверка логина/пароля, получение списка пользователей
Database → Server: список пользователей
Server → Client A: список пользователей
Client A → User A: отображает список
```

#### 3. Отправка приглашения

```
User A → Client A: выбирает User B и отправляет приглашение
Client A → Server: send_invitation(login, password, target_user, timeout)
Server → Database: проверка логина/пароля, создание приглашения
Database → Server: ID приглашения
Server → Client A: успех
Client A → User A: "Приглашение отправлено"
```

#### 4. Polling - получение приглашений

```
[каждые N секунд]
Client B → Server: get_invitations(login, password)
Server → Database: проверка логина/пароля, получение активных приглашений
Database → Server: список приглашений
Server → Client B: список приглашений
Client B → User B: показывает входящие приглашения
```

#### 5. Принятие приглашения

```
User B → Client B: принимает приглашение
Client B → Server: accept_invitation(login, password, invitation_id)
Server → Database: проверка логина/пароля, создание игры
Database → Server: game_id
Server → Client B: game_id
Client B → User B: "Игра началась!"
```

#### 6. Polling - получение состояния игры

```
[каждые N секунд]
Client A → Server: get_game_state(login, password, game_id)
Server → Database: проверка логина/пароля, получение состояния игры
Database → Server: состояние игры
Server → Client A: состояние (карты, счёт, чей ход)
Client A → User A: отображает игру
```

#### 7. Выполнение хода

```
User A → Client A: выбирает карту и кладёт её
Client A → Server: make_move(login, password, game_id, card_id)
Server → Database: проверка легальности хода, обновление состояния
Database → Server: новое состояние игры
Server → Client A: успех, новое состояние
Client A → User A: обновляет отображение
```

## Важные проверки сервера

На каждый запрос сервер проверяет:

1. **Аутентификация**: правильность логина и пароля
2. **Авторизация**: имеет ли пользователь право на это действие
3. **Валидация**: корректность параметров запроса
4. **Бизнес-логика**: соблюдение правил игры

### Примеры проверок:

- При получении состояния игры: пользователь участвует в этой игре?
- При ходе: сейчас ход этого игрока? карта принадлежит игроку? ход легален?
- При принятии приглашения: приглашение ещё активно? не истёк таймер?
- При объявлении марьяжа: у игрока есть король и дама одной масти?

## Безопасность

### Почему нельзя давать прямой доступ к БД?

Из лекции (стр. 4):

> "Сервер должен обеспечивать корректность работы при любых запросах, приходящих от клиентов (даже если эти запросы ошибочны или специально стремятся нарушить правила игры), так как клиент может быть создан кем угодно."

### Что может сделать злоумышленник с прямым доступом к БД:

- Читать карты противника
- Изменять счёт игры
- Нарушать правила игры
- Удалять чужие игры
- Изменять пароли других пользователей

### Решение: вся логика на сервере

- Клиент получает только свои данные
- Каждое действие проверяется сервером
- БД доступна только серверу
- Сервер как единая точка контроля

## Почему нужна аутентификация?

Из лекции (стр. 13):

> "Чтобы соперники не могли подглядеть скрытую информацию других пользователей, у каждого пользователя должен быть пароль, чтобы сервер предоставлял ему только доступную ему информацию."

### Что защищает аутентификация:

- Карты игрока (скрытая информация)
- Право на совершение действий (только свои ходы)
- Личные данные (статистика, история игр)
- Защита от подмены личности

## Таймауты и сроки действия

### Таймаут приглашения (стр. 14):

> "У приглашения есть «срок действия»: если оно не было принято за указанный срок, то оно становится недоступным (чтобы не произошло ситуации, когда отправитель приглашения не дождался принятия и ушёл, а в это время приглашение приняли и игра началась без него)."

### Таймлимит на ход:

- Каждый ход ограничен по времени (15/30/60 сек)
- При истечении времени - автоматическая победа противника
- Сервер проверяет таймауты при каждом polling-запросе

## Формат данных

### Запросы и ответы в JSON

Пример запроса:
```json
{
  "login": "Max_Krams",
  "password": "hashed_password",
  "action": "make_move",
  "game_id": 4821,
  "card_id": "K♥"
}
```

Пример ответа:
```json
{
  "success": true,
  "game_state": {
    "game_id": 4821,
    "your_cards": ["Q♥", "10♦", "A♠"],
    "trump": "♥",
    "score": {"you": 42, "opponent": 33},
    "table": [{"player": "you", "card": "K♥"}],
    "your_turn": false
  }
}
```

## Отличие от варианта с игровыми комнатами

**Не используется вариант со стр. 17-20**, потому что:

### Вариант с комнатами (НЕ для Шнопс 66):

- Пользователь создаёт игровую комнату с параметрами
- Указывается количество мест (может быть >2)
- Другие пользователи подключаются к комнате
- Игра начинается, когда все места заполнены

### Наш вариант с приглашениями (для Шнопс 66):

- Игра ВСЕГДА на 2 игроков (фиксировано)
- Прямое приглашение конкретного пользователя
- Игра начинается сразу при принятии приглашения
- Более простая логика для 1v1 игр

## Итоговая схема для Шнопс 66

```
┌─────────┐     ┌─────────┐     ┌────────┐     ┌──────────┐
│ User A  │────▶│Client A │────▶│ Server │────▶│ Database │
└─────────┘     └─────────┘     └────────┘     └──────────┘
                     ▲               │               │
                     │               ▼               │
                     └───────────JSON Response◀──────┘
                          (карты, счёт, ходы)

                          Polling каждые 3-5 сек
                          
┌─────────┐     ┌─────────┐          ▲
│ User B  │────▶│Client B │──────────┘
└─────────┘     └─────────┘     одновременный 
                                polling обоих клиентов
```
