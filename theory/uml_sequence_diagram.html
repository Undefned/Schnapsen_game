Конкретный вариант: Игра всегда для двух игроков с системой приглашений (стр. 14-16)

Почему именно этот вариант?

  • Шнопс 66 - игра строго на 2 игроков (не подходит вариант с игровыми комнатами)
  • Система приглашений между пользователями - пользователь видит список других пользователей и может отправить приглашение конкретному игроку
  • Приглашение имеет срок действия (таймер) - если не принято за время, становится недоступным

Клиент-серверная архитектура

Вариант 3 из лекции (стр. 12)

HTTP-клиент
→
API
HTTP-сервер
→
SQL-сервер
Ключевые принципы:
• API представляет собой набор HTTP-запросов
• Клиенты НЕ могут подключаться к SQL-серверу напрямую
• HTTP-сервер реализует логику игры и контролирует доступ

Тип взаимодействия: Polling (Short Polling)

  • Клиент периодически (каждые 3-5 сек) отправляет запросы серверу
  • Сервер сразу отвечает на запросы
  • Сервер НЕ может сам инициировать отправку данных клиенту

Почему нельзя давать прямой доступ к БД?

Из лекции (стр. 4): "Сервер должен обеспечивать корректность работы при любых запросах, приходящих от клиентов (даже если эти запросы ошибочны или специально стремятся нарушить правила игры), так как клиент может быть создан кем угодно."

Таймаут приглашения (стр. 14 лекции):
"У приглашения есть «срок действия»: если оно не было принято за указанный срок, то оно становится недоступным (чтобы не произошло ситуации, когда отправитель приглашения не дождался принятия и ушёл, а в это время приглашение приняли и игра началась без него)."

Игровой процесс

6. Polling - получение состояния игры (каждые N секунд)

Client A → Server
get_game_state(login, password, game_id) [автоматически]
Server → Database
Проверка логина/пароля, проверка что игра не закончилась, получение состояния
Database → Server
Состояние игры (карты, счёт, чей ход, стол)
Server → Client A
JSON с картами игрока, счётом, текущим ходом
Client A → User A
Обновляет отображение игры
Важно: Клиент получает ТОЛЬКО свои карты. Карты противника скрыты для защиты от читерства.

7. Выполнение хода

User A → Client A
Выбирает карту и кладёт её на стол
Client A → Server
make_move(login, password, game_id, card_id)
Server → Database
Проверка: сейчас ход этого игрока? карта принадлежит игроку? ход легален?
Database → Server
Новое состояние игры после хода
Server → Client A
Успех, обновлённое состояние
Client A → User A
Обновляет отображение (карта на столе)

8. Противник узнаёт о ходе через Polling

Client B → Server
get_game_state(...) [очередной polling-запрос]
Server → Client B
Новое состояние с картой User A на столе, теперь ход User B
Client B → User B
Показывает ход противника, теперь ваш ход

Проверки сервера на каждый запрос

Важные проверки

1. Аутентификация

Правильность логина и пароля. Без правильной пары логин/пароль запрос отклоняется.

2. Авторизация

Имеет ли пользователь право на это действие?

  • При получении состояния игры: пользователь участвует в этой игре?
  • При ходе: сейчас ход этого игрока?
  • При принятии приглашения: приглашение адресовано этому пользователю?

3. Валидация параметров

Корректность переданных данных:

  • game_id существует?
  • card_id корректный?
  • invitation_id существует и активен?

4. Бизнес-логика игры

Соблюдение правил игры:

  • Карта принадлежит игроку?
  • Ход легален по правилам Шнопс 66?
  • При объявлении марьяжа: у игрока есть король и дама одной масти?
  • Игра ещё не завершена?
  • Не истёк таймлимит на ход?
Цитата из лекции (стр. 13):
"Чтобы соперники не могли подглядеть скрытую информацию других пользователей, у каждого пользователя должен быть пароль, чтобы сервер предоставлял ему только доступную ему информацию."

Что защищается?

  • Карты игрока (скрытая информация) - клиент получает только свои карты
  • Право на действия - только свои ходы, нельзя ходить за противника
  • Личные данные - статистика, история игр
  • Целостность игры - нельзя нарушить правила, изменить счёт

Ключевые моменты

Архитектура
Вариант 3: HTTP-клиент → HTTP-сервер → SQL-сервер
Тип взаимодействия

JSON для запросов и ответов

Отличие от варианта с игровыми комнатами

НЕ используется вариант со страниц 17-20, потому что:

  • Вариант с комнатами: переменное количество игроков, игра начинается когда все места заполнены
  • Наш вариант: игра ВСЕГДА на 2 игроков, прямое приглашение конкретного пользователя
